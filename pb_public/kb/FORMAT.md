# Формат статей «Базы знаний»

Стартовые статьи лежат в `pb_public/kb/*.json` — по файлу на тему (`iphone.json`, `android.json`, `general.json`).
Каждый файл — JSON-массив статей. Владелец загружает их в CRM кнопкой «Загрузить / обновить стартовые статьи».
Статья с уже существующим `slug` обновляется новой версией из файла, только если владелец её не правил
(`kb_articles.seedHash` = хеш содержимого при загрузке, `kb-lib.contentHash`); правки владельца не теряются.

## Статья

```json
{
  "slug": "iphone-13",
  "title": "iPhone 13",
  "category": "Модель",
  "brand": "Apple",
  "deviceType": "Телефон",
  "models": ["iPhone 13"],
  "body": "## Коротко\n...markdown...",
  "sources": [{ "title": "Apple — Ремонт iPhone 13 (Self Service Repair)", "url": "https://support.apple.com/..." }],
  "checked": "2026-10-21"
}
```

- `slug` — латиница, цифры и дефис, уникален среди всех файлов.
- `category` — одно из: `Модель`, `Диагностика`, `Безопасность`, `Приём и выдача`, `Запчасти`.
- `brand` — `Apple`, `Samsung`, `Xiaomi`, `Honor`, `Huawei`, `realme`, `Tecno`, `Infinix` или `''` для общих статей.
- `deviceType` — `Телефон`, `Планшет`, `Ноутбук`, `Часы` или `''`.
- `models` — точные названия моделей так, как их пишут в заказе (`iPhone 13 Pro Max`, `Galaxy A52`, `Redmi Note 12`). По ним карточка заказа находит статьи: без марки, без слова «Телефон». Пустой массив — общая статья.
- `body` — Markdown, только этот набор: `##`/`###` заголовки, абзацы, списки `-` и `1.`, `**жирный**`, `*курсив*`, `` `код` ``, `[текст](https://...)`, таблицы `| a | b |` со строкой `|---|---|`, цитаты `>`. Без HTML и без картинок.
- `sources` — откуда факты, минимум один источник у каждой статьи с фактами о модели.
- `checked` — дата проверки источников.

## Разделы статьи о модели (порядок такой; раздел без проверенных фактов — пропустить)

1. `## Коротко` — 2–4 строки: год, особенности, о чём помнить мастеру.
2. `## Частые неисправности` — только подтверждённое (сервисные программы производителя, официальные бюллетени, признанные массовые дефекты). Для каждой: симптом → причина → что делать. Если подтверждённых нет — так и написать одной строкой.
3. `## При приёме проверить` — что проверить и записать до ремонта (Face ID / Touch ID, True Tone, камеры, следы вскрытия, вздутие, влага, «История запчастей»).
4. `## Ремонт: на что обратить внимание` — особенности разбора и сборки по официальному мануалу / iFixit: с какой стороны вскрывается, что отключать первым, клей, уплотнитель, известные ловушки (шлейфы, датчики). Без пошаговых инструкций — ссылкой на источник.
5. `## Запчасти и совместимость` — только документально подтверждённая совместимость (например, одна деталь у двух моделей). Серийная привязка деталей и что будет после замены неоригиналом.
6. `## Что сказать клиенту` — 2–4 честные фразы (влагозащита, Face ID, сообщение о неоригинальной детали, сроки).
7. `## Источники` — не писать: источники — в поле `sources`, CRM показывает их сама.

## Правила фактов — главное

- **Ничего не выдумывать.** Каждое конкретное утверждение (дефект, совместимость, особенность разбора) — из источника в `sources`. Нет источника — нет утверждения.
- Приоритет: официальные сайты производителей (support.apple.com, samsung.com/support, mi.com, honor.com), их сервисные мануалы и программы; затем iFixit (гиды и teardown); затем профильные издания. Форумы и маркетплейсы — не источник.
- Сомнительное помечать: «требует проверки».
- Никаких инструкций по обходу Activation Lock, FRP, Google-аккаунта, Mi-аккаунта, MDM, паролей, SIM-блокировок.
- Не выдумывать цены, сроки ремонта и гарантию «Эксперта».
- Пиши для мастера сервисного центра: коротко, по делу, по-русски.
